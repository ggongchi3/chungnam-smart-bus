## A와 B 사이의 인수인계

A는 `originStationId`, `destinationId`, `routeSearchId`, `routeOptionId`, `routeSnapshotVersion`, `dataMode`를 전달한다. 객체의 전체 예시와 필드 의미는 [API 계약 4절](api-contract.md#4-프론트엔드-a--b-공통-전달-데이터)을 기준으로 삼는다.

- 화면 상태 보관 방식과 라우터는 기술 스택 확정 후 결정한다. 두 담당자가 별도 앱이나 중복 API 클라이언트를 만들지 않는다.
- B는 전달받은 식별자로 상세 정보를 다시 조회한다. 버전 변경·만료·필수 ID 누락 시 갱신 또는 경로 재선택으로 안내한다.
- A는 선택 화면의 요약 값이 상세 화면의 최신 교통 사실을 대신한다고 가정하지 않는다. 데이터 모드도 서버 응답을 기준으로 확인한다.
- B는 현재 경로 상세를 기준으로 화면·음성·인쇄가 같은 구간 순서와 버전을 사용하도록 한다. 실시간 값과 인쇄물 생성 시각은 별도로 표시한다.

## 공통 접근성 구현 기준

다음은 이 프로젝트의 초기 설계 제안이다. 특정 표준 준수나 인증 완료를 뜻하지 않는다. 정확한 글꼴 크기·버튼 크기·대비 수치·간격과 적용 표준은 디자인 기준 수립 시 합의한다.

- A와 B 모두 큰 글씨와 충분한 터치 영역, 높은 명도 대비, 아이콘+텍스트, 색상에만 의존하지 않는 상태 표시를 구현한다.
- 키보드 이동, 보이는 초점, 의미 있는 요소와 이름, 읽기 쉬운 오류·로딩·결과 없음 상태를 함께 고려한다.
- A는 간결한 검색/선택 흐름과 현재 정류장 식별을, B는 구간 순서·갱신 시각·정보 확인 불가·인쇄 가독성을 확인한다.
- 음성 안내는 글 안내를 함께 제공하고 사용자가 재생·중지하도록 한다. 지원 불가·실패 시에도 핵심 텍스트 안내를 유지한다.
- 실제 장비의 터치·화면 시인성·스피커·프린터 사용성 검증은 브라우저 시제품 검토와 구분한다.

## 경로·AI·데이터 책임

백엔드는 데이터 검증·경로 계산·환승/도보 연결 확인·갱신 상태 판단을 맡는다. 사용할 계산 알고리즘과 지원 범위는 미정이다. 검증하지 못한 환승을 가능한 경로로 확정하지 않는다.

AI는 교통 사실의 출처가 아니다. 후보 ID는 제공된 목록 안에서만 선택하고, 안내는 허용 템플릿을 고른다. 노선·정류장·정류장 수·시간은 백엔드가 검증 결과로 채운다. AI 실패 시 일반 목적지 검색과 고정 안내 템플릿으로 대체한다. 핵심 검색·안내·인쇄 흐름이 AI 성공에 의존하지 않도록 설계한다.

2026-11-02부터 기본 백엔드 앱은 `ai.adapter.RuleBasedAIAdapter`를 연결한다. AI Python 폴더명은 `destination_interpretation`, `easy_guidance`를 사용한다. 공개 상태·이유 코드의 기준은 [API 계약 8절](api-contract.md#8-ai-목적지-표현-해석--추가-제안)이며 백엔드가 검증한 상태에서 이유 코드를 결정한다. A는 `matched`도 사용자 선택을 받고, 오타 추정 후보가 하나인 `needs_confirmation`도 확인 화면으로 처리한다.

## 충돌을 줄이는 작업 규칙 — 추가 제안

작업별 브랜치와 PR을 사용하고 최소 한 명의 동료 검토를 권장한다. 공통 설정·컴포넌트·계약을 바꾸는 PR은 위 대표 관리자와 영향받는 담당자가 검토한다. 실제 계정명·저장소 권한·브랜치 보호·CI 설정은 미정이며 자동 적용하지 않았다.

작업 파일을 처음 추가하는 담당자는 같은 최하위 폴더의 `temp`를 삭제한다. 다른 담당자의 폴더나 기존 파일을 일괄 교체하지 않는다.
