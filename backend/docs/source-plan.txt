첫 시연은 기존 개발 기준안에 맞춰 합성 정류장 5개·단방향 노선 2개·목적지 3개를 사용하고 직통·최대 1회 환승을 지원한다. 실제 충남 운행 데이터·외부 교통 API의 제공 범위는 미확인 상태다. 데이터 제공자와 분리한 시연 데이터 연결부터 완성하며 dataMode=demo를 유지한다.

기술은 Python·FastAPI·Uvicorn·Pydantic·SQLite·SQLAlchemy를 사용한다. 정확한 런타임·패키지 버전은 첫 단계에서 호환성을 확인한 뒤 고정한다. 테스트 도구는 pytest와 FastAPI TestClient를 추가하는 안으로 계획한다.

이 문서의 날짜별 작업 배분, DB 테이블·파일명의 세부안, 검증 항목은 백엔드 구현을 위한 추가 제안이다. 팀 합의가 완료되었다거나 기능이 이미 구현·검증되었다는 뜻은 아니다. 이번 작업은 계획서 작성이며 GitHub 변경이나 앱 코드 생성은 포함하지 않는다.

3. 단계별 실행 계획

1단계. 환경과 공통 처리 준비 — 10/26

목표: 다른 기능을 올릴 기본 서버와 공통 데이터 형식을 준비한다.

1. development-plan.md·api-contract.md·roles.md·data-sources.md를 읽고 맡은 API 8개와 오류·상태 규칙을 작업 목록으로 옮긴다.

2. AI 담당과 같은 Python 환경을 사용할 수 있도록 버전을 맞추고 가상환경·의존성을 준비한다. 설치가 확인된 버전을 잠금 또는 고정된 의존성 파일로 기록한다.

3. backend/main.py에 앱 진입점과 라우터 등록 구조를 만든다. 생성한 앱과 자동 API 문서 화면이 열리는지 확인한다.

4. API의 공통 응답 data / error / meta, requestId, generatedAt, dataMode와 공통 오류 모델을 정의한다. API JSON은 lowerCamelCase로 직렬화하고 내부 Python·DB 이름과 구분한다.

5. 입력 검증 오류를 프로젝트 계약인 400 INVALID_REQUEST로 변환하는 처리와 예외 응답 구조를 준비한다. 오류 응답에도 공통 봉투를 적용한다.

6. A와 프론트 5173·백엔드 8000, /api 개발 프록시, 로컬 주소 허용 범위를 맞춘다. 제출 형식·발표 제한시간·실행 URL 제출 필요 여부도 확인한다.

의존성 고정 파일은 Git으로 공유하고 가상환경 자체는 제외한다. 실제 비밀값을 넣지 않은 .env.example만 설정 예시로 공유하며 .env·키 파일은 커밋하지 않는다. 공통 설정이나 계약을 바꾸는 작업은 관련 담당자에게 검토를 요청한다.

산출물: 기본 서버, 의존성 버전 기록, 공통 응답·오류 스키마, 로컬 연결 기준.

완료 조건: 서버와 자동 문서 화면이 열리고 공통 형식의 성공/오류 응답을 검증할 수 있다. 현재 문서에 있는 고정 시각 예시는 설명용이므로, 실제 요청은 현재 출발 시각을 사용하도록 A에게 알린다.

2단계. DB와 시연 데이터 준비 — 10/27~10/28

목표: 이후 모든 기능이 같은 정류장·목적지·노선 자료를 사용하도록 만든다.

1. DB 저장 모델과 API 입출력 모델을 구분해 정의한다. DB 모델은 컬럼·관계, Pydantic 모델은 요청·응답 형식을 담당한다.

2. 5절의 테이블 세부안을 검토하여 키·관계·필수값을 정한다. 노선 경유지는 정류장 ID만으로 식별하지 않고 노선 ID와 순번을 함께 사용한다.

3. SQLite 연결과 요청별 세션·트랜잭션 정리를 구현한다. 외래키 제약이 실제로 활성화되도록 연결 설정과 동작을 확인한다.

4. 합성 데이터 원본과 초기 적재 기능을 만든다. 같은 적재 작업을 두 번 실행해도 중복 행이 생기지 않도록 한다.

5. backend/integrations/에 시연 데이터 제공 계층을 둔다. 서비스 로직에서 특정 외부 제공기관의 필드나 URL에 직접 의존하지 않도록 내부 모델로 변환한다.

6. A/B에게 정류장·목적지 목록, 경로 응답 초안, 정상/빈 결과/오류 JSON 예시를 전달한다. AI 담당과 등록 후보·구간·템플릿 입출력을 맞춘다.

필요한 실제 데이터의 출처·키·지원 범위는 docs/data-sources.md의 확인 항목으로 관리한다. 제공기관·공식 URL·자료명·확인일·범위·이용조건이 확인되지 않으면 확인 필요 상태를 유지하고 시연 데이터를 실제 운행 데이터로 바꾸지 않는다.

산출물: DB 모델, 합성 원본 데이터, 초기 적재 기능, 데이터 제공 계층, 공통 응답 예시.

완료 조건: 정류장 5개·노선 2개·목적지 3개·경유 행 6개·명시적 환승 연결 1개를 확인한다. 재적재 후에도 수량이 유지되고 잘못된 참조가 거부된다. DB 실행 파일은 backend/.local/에 두며 Git 추적 대상에서 제외한다.

3단계. 정류장·목적지 조회 API — 10/29~10/30

목표: A가 실제 서버로 시작 화면과 목적지 검색을 연결한다.

1. 정류장 ID로 이름·방향 등 현재 정류장 정보를 조회한다. 미확인 좌표·지역 값은 계약에 맞게 null로 둔다.

2. 목적지를 이름·별칭·분류로 검색한다. query와 category를 함께 주면 교집합으로 처리한다.

3. 등록되지 않은 출발 정류장은 404, 잘못된 분류/입력 길이는 400, 검색 결과 없음은 200과 빈 배열로 구분한다.

4. DB 조회 결과를 Pydantic 응답 모델로 변환해 타입·필수 필드·null 처리를 확인한다.

5. A의 실제 브라우저에서 조회하고 경로·포트·필드명 불일치를 해결한다.

산출물: 정류장 조회와 목적지 검색 API 2개, A와 확인한 요청·응답 사례.

완료 조건: 시작 정류장이 표시되고 병원·시장·터미널 선택/검색이 서버 데이터로 동작한다. A가 임시 응답을 사용하는 부분과 실제 API를 사용하는 부분을 구분할 수 있다.

4단계. 경로 검색과 상세 안내 API — 10/31~11/1

목표: 목적지 선택부터 상세 이동 안내까지 첫 전체 연결을 만든다.

1. 출발·목적지 ID와 departAt을 검증한다. departAt은 서버 시각과 절댓값 120초 이내인 현재 출발 조회로 제한한다.

2. 같은 노선에서 출발 순번이 하차 순번보다 앞서는 직통 후보를 찾는다. 역방향 경로를 자동으로 만들지 않는다.

3. 명시적으로 등록된 환승 연결을 통해 최대 1회 환승 후보를 찾는다. 정류장 이름·좌표가 같다는 이유로 환승을 생성하지 않는다.

4. 각 후보를 순서 있는 bus/walk/transfer 구간으로 구성한다. 검증되지 않은 거리·소요시간과 전체 이동시간은 null로 유지한다.

5. 환승 수 → 버스 정류장 수 합계 → 안정적인 경로 키 순으로 정렬하고 중복을 제거하여 최대 3개를 반환한다. 안정적인 키는 노선 ID와 승하차 순번 조합으로 만드는 안을 사용한다.

6. routeSearchId·routeOptionId·routeSnapshotVersion·expiresAt을 생성하고 검색 스냅샷을 저장한다. 같은 검색의 상세 조회는 같은 구간 순서를 사용하도록 한다.

7. A→B 전달 객체의 6개 필드를 확인하고 B가 선택한 경로의 상세를 서버에서 조회하도록 연결한다.

산출물: 경로 검색·상세 API, 직통/환승 조합 로직, 검색 스냅샷 저장, A→B 연동 결과.

완료 조건: 출발 001에서 시장은 직통 1정류장, 병원은 직통 2정류장, 터미널은 003에서 1회 환승하여 총 버스 4정류장을 이동한다. 이는 합성 경로 안의 결과다. 화면에 선택한 경로와 상세 구간이 일치하고, 경로 없음은 200과 빈 경로 배열로 처리한다.

5단계. 도착·운행 변경·시간·버전 처리 — 11/2~11/4

목표: 정상·변경·미수신·오래된 정보를 구분해 B에게 전달한다.

1. 시연 제공자가 도착 값·운행 상태·시간표 변경·결행·우회·미수신을 반환하도록 시나리오를 만든다. 모든 값은 demo 모드로 표시한다.

2. sourceUpdatedAt, fetchedAt, generatedAt을 분리한다. sourceUpdatedAt이 없거나 미래이면 unknown, 0~90초 전이면 fresh, 90초 초과이면 stale로 판단한다.

3. 도착 값이 없는 상태를 결행으로 변환하지 않는다. 운행 변경을 조회하지 못하면 변경 없음 대신 coverageStatus=unknown을 반환한다.

4. 현재 적용이 확인된 결행·우회 등으로 경로 이용이 불가능해지면 재검색하도록 한다. 경유 순서·연결·적용 운행 변경은 경로 버전에 반영하고 단순 ETA 갱신은 버전을 유지한다.

5. 저장된 검색의 존재 여부·10분 만료·현재 경로 버전을 상세/live/안내문/인쇄 준비에서 공통으로 검사하도록 기능을 묶는다.

6. B와 30초 조회, 5초 클라이언트 제한시간, stale/unknown 표시를 맞춘다. 조회 타이머와 화면 표시 자체는 B가 구현한다.

산출물: live API, 시연 상태 데이터, 최신성 판단, 검색 만료·버전 검증 기능.

완료 조건: 같은 경로에 대해 정상·미수신·오래됨·운행 변경을 구분한다. 만료는 410, 버전 불일치는 409, 확인된 경로 이용 불가는 409의 해당 서비스 코드로 반환한다. 구체적인 코드 선택 우선순위는 테스트 기대값으로 고정한다.

6단계. AI 중계와 인쇄 데이터 API — 11/5~11/6

목표: AI 결과를 검증하고 화면·음성·인쇄가 같은 경로를 사용하게 한다.

1. AI 담당의 Python 모듈을 합의한 함수 입력·출력으로 연결한다. 현재 하이픈으로 된 AI 작업 폴더를 Python 패키지로 정리할 때는 AI 담당과 참조 변경을 함께 처리한다.

2. 목적지 해석에는 등록된 후보만 전달하고 반환 ID가 그 목록 안에 있는지 검사한다. 목록 밖 ID나 모호한 후보를 임의 장소로 확정하지 않는다.

3. 쉬운 안내는 구간 ID·순서·허용 templateId를 검증한 후 서버가 노선·정류장·정류장 수를 채운다. AI가 교통 사실을 변경하지 못하도록 한다.

4. AI 실패·잘못된 출력·결과 채택 예산 1초 초과를 일반 검색 또는 고정 템플릿으로 대체한다. 고비용 모델 실험의 실제 실행과 응답 대기 제한은 구분하여 기한이 지난 결과를 채택하지 않는다.

5. 인쇄 요청에서 검색 만료·경로 상태·expectedRouteSnapshotVersion을 다시 확인하고 경로 상세·운행 정보·생성 시각을 하나의 출력 준비 스냅샷으로 고정한다.

6. B에게 준비된 안내문과 인쇄 JSON을 전달한다. 화면·음성·인쇄가 같은 버전과 구간 순서를 사용하는지 확인한다.

산출물: 목적지 해석·쉬운 안내·인쇄 준비 API, AI 출력 검증과 대체 처리, 출력용 스냅샷.

완료 조건: 서비스 API 8개가 1차 구현된다. AI가 실패해도 핵심 흐름이 유지되고 미확인 교통 사실이 추가되지 않는다. ready 경로는 도착 미수신을 명시하고 인쇄할 수 있으며, 확인된 이용 불가·버전 변경·만료는 재확인으로 안내한다.

역할 경계: 음성 재생·중지, 인쇄 버튼·CSS·브라우저 인쇄는 B의 작업이다. 백엔드는 검증된 경로·텍스트·출력 데이터를 제공하고 종이 출력 성공 여부를 판정하지 않는다.

transfer_connections는 route_stops의 노선·순번 조합을 참조한다. 첫 시연은 demo-route-001의 3번 경유 지점에서 demo-route-002의 1번 경유 지점으로 연결한다. 같은 demo-stop-003을 이용하는 합성 연결이며 실제 환승 검증 결과가 아니다.

검색 후보와 구간 스냅샷은 직렬화한 JSON을 텍스트로 저장하는 안을 사용하여 초기 테이블 수를 제한한다. 이때도 저장 전·읽은 후 스키마를 검증하고 DB 저장 형식과 외부 응답을 구분한다. 시간 저장 형식은 UTC epoch 초로 통일하고 응답 시 시간대가 있는 ISO 8601로 변환하는 안을 검토한다.

ORM 테이블과 Pydantic 입출력 모델을 같은 것으로 취급하지 않는다. 실제 컬럼·nullable·관계와 JSON 필드 이름을 별도로 확인하고, 프론트에서 사용하는 타입과 함께 변경한다.
